## Selected order

1. Close existing HTTP and Dapper correctness defects with regression evidence.
2. Implement the opt-in transaction/session boundary and exercise EF/Dapper rollback on PostgreSQL.
3. Correct idempotency ownership and commit ordering against that boundary.
4. Reconcile conventions, active roadmap and package registry with verified implementation.
5. Complete background work, cache invalidation, full-row write guards, translation and identity in
   their own vectors; each requires its actual contract and provider evidence.

## Data-session design decisions

- `DbContext` retains tracking, queries and `SaveChangesAsync`. The new session owns an explicit
  transaction spanning EF and raw SQL; it is not a replacement repository or change tracker.
- No registration through `AddApiDefaults` or `AddPostgresPersistence`: callers opt into the session.
- A singleton `IDbConnectionFactory` remains independent for migrations and autonomous operations.
- Missing ambient tenant retains the owner's existing system/admin meaning. The older fail-closed
  proposal in the July architecture and test plan is superseded by its own owner-rulings section.
- Commit hooks run only after the database commit succeeds. Hook failures cannot make a committed
  transaction look rolled back. In-memory hooks provide no crash durability.
- Retrying execution strategies cannot wrap user-controlled transactions without replaying work;
  reject incompatible registration/usage rather than silently replaying external effects.
- Nesting, EF tracker recovery, hook deduplication and idempotency ordering need explicit tests.
  A database savepoint alone does not restore tracked CLR objects or concurrency tokens.

## External contract references

- [EF Core transactions](https://learn.microsoft.com/en-us/ef/core/saving/transactions): EF/raw-SQL
  sharing requires the same connection and transaction; automatic retries conflict with manual units.
- [EF Core context pooling](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics):
  application-owned state and driver state require explicit lifecycle handling.
- [SocketsHttpHandler proxy behavior](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.useproxy?view=net-10.0):
  proxy use is enabled by default; a connect callback must not mistake a proxy for the destination.

## Next implementation cuts

1. **Scoped background work.** Bounded channel, admission/backpressure, per-item DI scope,
   explicit cancellation ownership and shutdown drain. Test host shutdown with queued/in-flight work;
   preserve durable product claim stores instead of substituting an in-memory queue for them.
2. **Cache completion.** Use completion callbacks for local eviction; test rollback discards invalidations.
   Add distributed invalidation with explicit delivery/reconciliation semantics before promising cross-host coherence.
3. **Full data pipeline.** Build EF-model-derived read metadata, value-converter/owned-column materialization,
   `FullRow` provenance and pooled-context write guards. Add manual flush only with explicit semantics.
   Test stale xmin, detached defaults, duplicate tracked instances, mutable graphs and pool reuse.
4. **Translation and identity.** Implement resx error mappers/fallback/pseudo-localization before broad message
   formatting. Identity recovery, refresh/revocation and cookie/CSRF flows retain their dedicated design/test gates.
5. **Durable idempotency.** Add persistent ownership/replay and reconciliation when multi-host or crash durability
   becomes a consumer requirement. The in-memory implementation deliberately cannot promise exactly-once effects.
